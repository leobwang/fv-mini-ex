# fv-mini-ex design and authoring spec

Mini exercises for writing proofs and verified programs in **Lean 4**, **Dafny** and **Verus**.
This file is the contract every problem must meet. Learner-facing docs are `README.md`,
`<lang>/REFERENCE.md` and `<lang>/INDEX.md`.

## 1. Goals

- Hands-on in seconds: open a file, read a ≤12-line reference card (Lean: the problem's skeleton and its
  guide, §12), fill the holes, run `./check`.
- Cover a wide range of syntax quickly. Each easy problem introduces about **one** new construct, in
  syllabus order, so the easy tier works as a tour of the language.
- Learner: knows the basics of formal verification and has seen the language, but has not
  memorized its syntax or library. Strong CS/math background (graduate-level CS, undergrad math).
- Every problem is machine-checked: the stub type-checks and fails, the reference solution passes.

## 2. Shape

Dafny and Verus: **100 problems each = 45 easy (E01–E45) + 45 medium (M01–M45) + 10 hard (H01–H10).** Lean has grown past this: 127 easy, 192 medium, 115 hard (see §11).

| Tier | Budget | Typical solution size | What it exercises |
|---|---|---|---|
| easy | 1–3 min | 1–8 lines | one new construct or tactic, applied once |
| medium | 5–20 min | 5–40 lines | combine 2–4 constructs; a loop invariant, an induction with a helper lemma, a data-structure invariant |
| hard | 30 min–2 h | 40–200 lines | a classic verified algorithm/data structure or a real theorem; ships with **milestones** |

Each header gives a time estimate within its tier's band (e.g. `2-3 min`, `10-15 min`, `1-2 h`).

**Shared problems:** ~20 problems appear in all three languages, tagged `[Rnn]` (§7), so a learner
can compare them. The rest of each track targets that language's own features (§8).

## 3. Layout

```
check                      ./check [--solutions|--stubs|--freeze|--index] [lang] [ID...]
tools/check.py             the checker (stdlib Python 3; do not edit as an agent, report issues instead)
tools/setup.sh             pinned toolchains -> .toolchain/ (Linux x86-64, macOS arm64/x86-64)
VERSIONS.md                pins
<lang>/easy|medium|hard/   stubs: E07_snake_name.<ext> (Dafny, Verus)
<lang>/solutions/<tier>/   reference solutions, same file names (Dafny, Verus)
lean/<tier>/[<topic>/]<ID>_<name>/   one folder per Lean problem: problem.lean, solution.lean,
                           guide.lean, cheatsheet.md (§12)
lean/TACTIC_STATES.md      generic tactics as before/after proof states, shared by every Lean guide
tools/guide_sync.py        checks every Lean guide folder (§12)
<lang>/specs.json          frozen spec hashes + banned names (generated by --freeze)
<lang>/INDEX.md            generated by --index
<lang>/SYLLABUS.md         author's plan: each ID -> title, new constructs, Rnn
<lang>/REFERENCE.md        cumulative learner cheat sheet

```

File name: `<ID>_<snake_case_title>.<ext>`, e.g. `M07_binary_search.dfy`. IDs are dense (E01..E45).

## 4. Problem file anatomy

Every file has four parts, in order:

1. **Header line** (first line, machine-parsed): `<comment> ID | Title | time | tags [Rnn]`.
   Tags are comma-separated constructs/topics; add `mathlib` for Lean files that import Mathlib.
2. **Card** (same comment block; Lean problems use the §12 header instead): `GOAL` (1–3 lines: what to prove/implement, in words) and
   `REFERENCE` (≤12 lines, ideally 4–8). The reference lists **only** the syntax, tactics and library
   names this problem needs and that are new or easy to forget, each as a real, compilable
   one-line example plus a short `--`/`//` gloss. Never a full solution. Optional extra lines:
   `BANNED: Name.one, Name.two` (library lemmas that would trivialize it; the checker enforces this),
   `NOTE:` (one line on a trap such as overflow or nat subtraction).
3. **Body**: code with one or more `BEGIN SPEC` / `END SPEC` regions (§5) and holes.
4. **Hints** at the end, below a banner containing the word `HINTS`, in a comment:
   - `H1.` a nudge (what to look at)
   - `H2.` the strategy (which induction, which invariant shape, which lemma family)
   - `H3.` the key line (the invariant, the lemma statement, the crucial tactic call). Still not the
     whole solution.

Comment syntax: Lean `/- ... -/` and `--`; Dafny and Verus `//` and `/* ... */`.
The E01 files in each language are the canonical examples. **Copy their format exactly.**

### Holes

| Lang | Proof hole | Code hole |
|---|---|---|
| Lean | `sorry` | `sorry` (in a `def` body) |
| Dafny | empty body `{ }` (lemma), or a body missing steps | method body `{ }`, function body `0 // TODO` or a placeholder of the right type |
| Verus | empty `proof fn` body `{ }` | exec body returning a typed placeholder: `0 // TODO`, `Vec::new() // TODO`, `false // TODO` |

Stubs must **type-check** (`./check --stubs` runs `lake env lean` / `dafny resolve` / `verus --no-verify`)
and must **not already pass**. Each spec region should fail on its own as stubbed; avoid a
lemma the verifier proves with an empty body.

## 5. Specs are frozen

`BEGIN SPEC` / `END SPEC` (inside line comments) wrap what the learner must not change:
signatures, `requires`/`ensures`, theorem statements, datatype definitions the spec depends on,
and spec functions the statement refers to. `./check --freeze <lang>` hashes the regions (trailing
whitespace ignored). The learner check fails if a region changes, disappears, or is added.

- Lean: put the statement through `:=` inside the region and the proof hole after `END SPEC`:
  ```lean
  -- BEGIN SPEC
  theorem foo (n : Nat) : n + 0 = n :=
  -- END SPEC
    sorry
  ```
  Every `theorem/lemma/def/abbrev/instance` inside a region must be **named**; the checker runs
  `#print axioms` on each and allows only `propext`, `Classical.choice`, `Quot.sound`. A spec
  region inside `namespace X` is fine (the checker qualifies names). Prefer one
  `namespace <ID>` per file when names could clash with core/Mathlib (`reverse`, `sum`, `Sorted`…).
- Dafny/Verus: the region holds the signature and contracts; the body `{ ... }` comes after `END SPEC`.
- Learners may add helper lemmas, functions and ghost code anywhere outside the regions.
- Definitions the learner must *write* (e.g. "implement `rev`") have their signature in a region
  and their body as a hole. The theorems about them constrain them.

Conventions learned while authoring:
- A marker counts only on a line of its own (`-- BEGIN SPEC` / `// END SPEC`).
- `BANNED:` matches the **last** name component anywhere outside spec regions (so `open Nat` can't
  dodge it). Avoid banning names whose last component collides with something the learner needs,
  such as banning `OrderHom.lfp` when the problem defines its own `lfp`. It can also ban tactics or
  keywords (e.g. `BANNED: by` forces term mode).
- Dafny proves simple inductive lemmas automatically. Mark such spec lemmas `{:induction false}` so
  the stub fails, and say why on the card.
- When the lesson is to add a clause inside a frozen signature (`reads`, `decreases`), split the
  declaration into two spec regions with an editable line between.
- Dafny turns trigger/matching-loop warnings into errors. Problems that need `{:trigger}` say so on
  the card.

Forbidden in learner code (comments are ignored): Lean `axiom`, `native_decide`, `implemented_by`,
`extern`, `unsafe`; Dafny `assume`, `expect`, `{:axiom}`, `{:extern}`, `{:verify false}`, `{:only}`;
Verus `assume(`, `admit(`, `verifier::external*`, `assume_specification`, `#[cfg`, `unsafe`
(plus Verus runs with `--no-cheating`; Dafny treats warnings as errors, which rejects bodyless lemmas).
Solutions obey the same rules.

## 6. Toolchains and limits

Lean 4.32.0 + Mathlib v4.32.0 (`lean/`); Dafny 4.11.0; Verus 0.2026.09.27.3cf1832 (Rust 1.98.1).
Dafny `--resource-limit 10M` per check for learners, **5M for solutions**; Verus `--rlimit 10` for
learners, **5 for solutions**. Solutions are checked at the strict limit so they keep headroom
on other platforms. Lean: default heartbeats; no `set_option maxHeartbeats` in solutions.
Verus files are checked with `--crate-type=lib` (no `fn main` needed) and must start with
`use vstd::prelude::*;` and put everything inside `verus! { }`.
Lean files that don't use Mathlib must not import it (they load faster); Mathlib files start with
`import Mathlib`.

## 7. Shared problems (Rnn)

Same idea in every language; adapt the data types (Lean: `List`/`Nat`/`Int`; Dafny: `array`/`seq`;
Verus: `Vec`/`u64`/`i64` with overflow preconditions). Tier may differ by language when the
difficulty genuinely differs (e.g. overflow makes Verus harder); suggested tier in brackets.

| R | Problem | Spec (language-neutral) | Tier |
|---|---|---|---|
| R01 | Absolute value | r ≥ 0 ∧ (r = x ∨ r = −x) | E |
| R02 | Max of two | r ≥ a ∧ r ≥ b ∧ (r = a ∨ r = b) | E |
| R03 | Sum 0..n by loop/accumulator | result = n(n+1)/2 (Lean: `2 * sumTo n = n * (n+1)`) | E/M |
| R04 | Linear search | returns index of first occurrence of key, or −1/none; none ⇒ key ∉ a | M |
| R05 | Max element of non-empty array | ∀i, a[i] ≤ r ∧ ∃i, a[i] = r | M |
| R06 | Count occurrences | result = spec-level count | M |
| R07 | Reverse | out[i] = in[n−1−i] (in place for Dafny/Verus; Lean: accumulator rev = spec rev) | M |
| R08 | Is sorted | returns true ⇔ ∀ i<j, a[i] ≤ a[j] | M |
| R09 | Binary search on sorted array | some i ⇒ a[i] = key; none ⇒ key ∉ a (Verus: overflow-safe midpoint) | M |
| R10 | Fibonacci, iterative = recursive spec | result = fib(n) (Verus: requires fib(n) fits) | M |
| R11 | Fast exponentiation | result = b^e, O(log e) by squaring | M |
| R12 | Integer square root | r² ≤ n < (r+1)² | M |
| R13 | GCD by Euclid | result = spec gcd (or: divides both and every common divisor divides it) | M |
| R14 | Insertion sort | sorted ∧ permutation (multiset equality / `List.Perm`) | H (Lean M-H ok) |
| R15 | Merge two sorted sequences | sorted ∧ multiset(out) = multiset(a) + multiset(b) | M |
| R16 | Dedup a sorted sequence | strictly increasing ∧ same element set | M |
| R17 | Palindrome check | returns true ⇔ ∀i, s[i] = s[n−1−i] | M |
| R18 | Prefix sums | out[i] = Σ_{j<i} a[j] | M |
| R19 | Dutch national flag (3-way partition) | permutation ∧ three contiguous regions | H |
| R20 | Merge sort | sorted ∧ permutation | H |

E01 is R01 in Dafny and Verus. Lean's E01 is the toolchain warm-up, so Lean places R01 elsewhere.

## 9. Quality bar

- Specs say what is meant. A spec must rule out trivial solutions (e.g. a sort spec needs sorted
  **and** permutation; a search returning "not found" needs `key ∉ a`). Lean theorems about a
  learner-written `def` must pin down its behaviour.
- Reference cards are accurate at the pinned versions. Every library name in a card must exist
  (Lean: `#check` it; Dafny/Verus: use it in the solution or a probe). Prefer showing the shape of a
  call over naming many lemmas.
- Hints climb from nudge to near-solution. H3 for a loop problem gives the invariant; for an induction
  it gives the induction command and the helper lemma's statement.
- Solutions are idiomatic and short, and pass at the strict limit. Add at most a few `-- WHY:` /
  `// WHY:` comments where there is a classic trap (missing `decreases`, an invariant that's too weak, a
  trigger that never fires, nat subtraction, overflow).
- Hard problems: give 2–5 **milestones** outside the spec regions, marked
  `MILESTONE (optional: change or delete)`, each a helper lemma/function statement with a hole. The
  learner can prove them, change them, or ignore them. In the solution, milestones are proved.
- No duplicates: each problem must teach something the previous ones don't.
- Time budgets are honest for the learner in §1, not for the author.

## 10. Authoring workflow (per language)

1. Write `<lang>/SYLLABUS.md`: a table of all 100 IDs → title, new construct(s), tags, Rnn. Check it
   against §7 and §8 before writing problems.
2. Write problems in batches (~10): stub in `<lang>/<tier>/`, solution in `<lang>/solutions/<tier>/`
   (Lean: `problem.lean` and `solution.lean` in the problem's folder, plus its guide, §12).
   Copy the stub to the solution first, then fill the holes, so the spec regions are byte-identical.
3. After each batch: `./check --freeze <lang>`, then `./check --stubs <lang> <IDs>` and
   `./check --solutions <lang> <IDs>`. Fix until both pass. (`-j 4` is the default; keep it.)
4. Write `<lang>/REFERENCE.md`: a cumulative cheat sheet grouped by topic (not by problem), dense
   tables and code, each entry pointing to the problem IDs that use it. End with a `## Cheatsheet`
   section: the 30–50 most-used items on one screen.
5. `./check --index <lang>`, then a final full `./check --stubs <lang>` and `./check --solutions <lang>`.

## 11. Lean track v2: three tiers of ~100, topics, domain libraries

The Lean track grows to at least 100 problems per tier. The counts are **targets, not caps**: go
past them whenever a problem teaches something the others don't, and never pad to reach them.
Dafny and Verus keep §2.

**IDs and layout.** Lean IDs have 3 digits (`E001`, `M041`, `H063`) and are dense, in teaching
order: easy E001–E127; medium M001–M192 and hard H001–H115, numbered contiguously topic by topic in
the order of the table below. Easy problem folders sit flat in `lean/easy/`. Medium and hard problem folders sit in
topic folders, `lean/<tier>/<NN_topic>/<ID>_<name>/` (§12). To add problems, append
new IDs at the end of a tier (or within a topic, then run `tools/lean_renumber.py` with a mapping to
re-densify; it rewrites file names, headers, namespaces and cross-references, then refreeze).
Freeze only the IDs you touch: `./check --freeze lean M041 M042` (locked, merges into `specs.json`).

**Easy tier.** E001–E094 are the syntax and tactics tour (core first, then Mathlib automation and
notation). E095–E127 are domain warm-ups that introduce each new library's core definitions so medium
problems don't start cold: E095–E103 probability, E104–E108 numerics, E109–E114 quantum,
E115–E121 condensed matter, E122–E127 PhysLean.

**physlib.** Pinned in `lean/lakefile.toml` (commit `ba2a946`, the last one on Lean v4.32.0; same
Mathlib rev). Import the specific modules a problem needs (`import Physlib.CondensedMatter.…`,
`import QuantumInfo.States.…`), not the whole library, and tag the header `physlib`. physlib contains
`sorry`s. **Every physlib/QuantumInfo constant that a spec mentions must be sorry-free**: run
`#print axioms` on it while authoring. A spec built on a sorried definition is meaningless, and a
solution that uses a sorried lemma fails the checker's axiom gate.

**Domain problems must really be about the domain.** A probability problem states a probability
fact (Markov/Chebyshev, independence, Bayes, expectation of a concrete distribution); a quantum
problem states a fact about states, gates, measurement or entanglement; a condensed-matter problem
is about a lattice model, Hamiltonian, partition function or band structure; a PhysLean problem
uses physlib's own types. No arithmetic in disguise. The learner studies physics and CS, so cards
explain **library notation and API**, not physics. Still, define any symbol the statement uses at
first appearance.

**Tier honesty check.** Before a medium/hard problem is final, try each of `simp`, `simp_all`,
`aesop`, `grind`, `norm_num`, `decide`, `omega`, `linarith`, `nlinarith`, `positivity`, `fun_prop`,
`exact?` and `try?` on its main spec, in a probe file that does not contain the solution. If one
closes it, either strengthen the spec, move the problem to easy, or (only when the point of the problem
is the manual technique) ban the closing automation on the card (`BANNED: grind, try?`).

**Frozen meaning, not just frozen text (Lean).** `--freeze` also compiles the stub and records, for
every named declaration in a spec region (theorem, lemma, def, abbrev, instance, inductive, structure,
class), a hash of its fully explicit (`pp.all`) elaborated type. For defs, abbrevs and instances
that the stub already gives (sorry-free), it also records a hash of the value. The checker
recomputes these, so a `variable`/`include`, `open`, instance, notation or macro added outside the
spec that changes what a frozen statement means is caught (verified against injected-variable and
instance-override attacks). Consequences for authors: every spec declaration needs a name; and
helper code in a solution must not change the elaborated spec (it never does in normal code).

**`AXIOMS:` card line (Lean).** `AXIOMS: propext, Quot.sound` narrows the axioms a solution may
use (default: `propext, Classical.choice, Quot.sound`). Use it for constructive problems, e.g.
"derive excluded middle from choice" must not use `Classical.choice` itself. Frozen like `BANNED`.

**physlib modules.** `lake build Physlib QuantumInfo` builds only what the two library roots import,
plus 7 orphan modules built separately. Four orphan modules are broken upstream and unusable:
`QuantumInfo.Regularized`, `QuantumInfo.ResourceTheory.ResourceTheory`,
`QuantumInfo.Entropy.Axiomatized.{Defs,Renyi}`. Import only modules that have a `.olean` under
`lean/.lake/packages/physlib/.lake/build/lib/lean/`.

## 12. Lean problem folders and guides

Every Lean problem is a folder `lean/<tier>/[<topic>/]<ID>_<name>/` with four files. The goal: a
learner who knows only Lean basics (the syntax tour E001–E033) and has never used Mathlib or physlib
can finish the problem from these files alone. `lean/medium/08_quantum_computing/M126_hadamard_gate/`
is the canonical example. **Copy its format.**

| File | What it is |
|---|---|
| `problem.lean` | the stub: header, GUIDE block, a SKELETON before each spec theorem, the spec, HINTS |
| `solution.lean` | the reference solution: the same file with the holes filled |
| `guide.lean` | runnable examples, one per tactic or lemma the problem needs; the learner steps through them in the infoview |
| `cheatsheet.md` | the same entries as text, one section per hole, with before/after proof states |

`./check lean ID` reads `problem.lean`, `./check --solutions lean ID` reads `solution.lean`, and
`tools/guide_sync.py ID` checks the guide. All three must pass for every problem.

### problem.lean

1. **Header comment:** line 1 is the machine-read header (§4). Then `GOAL` (1–3 lines). Then card
   lines the checker reads, verbatim: `BANNED:`, `AXIOMS:`. Then a `GUIDE` block:
   ```
   GUIDE
     Entries R1–Rn: one per tactic or lemma, with the proof state before and after.
       cheatsheet.md   read
       guide.lean      step through in the infoview
     Each theorem below has a SKELETON: the order in which those entries are used.
   ```
   There is **no `REFERENCE` card and no `NOTE:` line**: their content belongs in the guide (a NOTE
   becomes a trap in the cheatsheet).
2. **SKELETON:** a `/- SKELETON · <name> … -/` comment directly before the `-- BEGIN SPEC` of every
   spec theorem or lemma with a hole (and before a spec `def` whose body is a hole). It gives the
   proof's overall structure as numbered steps, and for each step the guide entries it uses, in the
   order they are applied (`R3, R4`, `R13 → R14 → R15`). A step may name a fact to prove first
   (`h : (√2 : ℂ)⁻¹ * (√2 : ℂ)⁻¹ = 1 / 2`) or a milestone to use. It never contains a complete
   tactic proof. Generic tactics from `lean/TACTIC_STATES.md` may be named directly (`rw [h]`).
   Hard problems: the skeleton says which milestones to prove first and where they are used.
3. **Spec and holes:** unchanged. Spec regions are frozen (§5).
4. **HINTS** (§4): `H1` nudge → `H3` key line, consistent with the guide and the skeleton.

`solution.lean` gets the same header, GUIDE block, skeletons and hints; only its proofs differ.

### guide.lean

- Imports what the problem imports, and nothing more (no `import Mathlib` in a core problem's guide).
  Its declarations live in `namespace <ID>Guide`.
- **Part R, reference entries R1…Rn:** one per tactic or library lemma the solution uses, except the
  generic tactics in `lean/TACTIC_STATES.md` (which may still get an entry when the problem leans on
  them in an unusual way). Each entry is a doc-comment heading
  ``/-! ### Rk. `tactic or lemma` · what changes: goal, context, or goal list -/`` and a **minimal**
  `example` stated with **typed symbolic placeholders**: `{α : Type} [DivisionCommMonoid α] (a b : α)`,
  a predicate `P : α → Prop` for "the rest of the goal", and a hypothesis `h` whose only job is to show
  what the goal became. One tactic step per entry where possible, so the infoview shows exactly one
  before and one after state. Not long concrete examples.
- **Part W, worked combinations W1…:** a few short examples that chain entries the way the skeleton
  does, on objects that are not the problem's (other matrices, `√3` instead of `√2`, another list
  function). Optional for easy problems.
- **No spoilers:** never restate a spec declaration or prove the problem's theorem (or a renamed
  copy). `guide_sync.py` rejects any spec line it finds in the guide.
- **No banned names:** a guide never uses a name on the problem's `BANNED:` line.
- No `trace_state`, no `#guard_msgs`, no pinned output, no `sorry`, no warnings. Plain examples.

### cheatsheet.md

In this order: title `# <ID> · <Title>: cheatsheet`; links to `problem.lean`, `guide.lean` and
`lean/TACTIC_STATES.md`; **Assumed** (Lean basics, plus any earlier problem it builds on) and **New
here** (the libraries and notions it introduces); *How to read an entry*; *Reading the goals* (a
table from each piece of notation the learner will see in the infoview to its meaning); one section
per hole, `## Part k · <name>` with its statement in words and its entries; *Traps*; and a final
`## Cheatsheet` table (Need · Write · Entry).

Each entry: **`Rk · tactic`** changes the **goal** / **context** / **goal list**: one sentence on
what it does, the lemma's statement when it is a lemma, and its placeholders with their types (say
which familiar types meet a type-class bracket). Then a `| Before | After |` table of proof states
(`Γ ⊢ G`, showing only the hypotheses that change). Every `⊢` cell in a table row and every line of a
```` ```lean-goal ```` block must be a state that Lean reaches in `guide.lean`, copied from the
infoview; `guide_sync.py` checks this by compiling an instrumented copy.

### Checks

```
./check lean ID                 # the stub type-checks and is not yet solved (TODO)
./check --stubs lean ID         # header, frozen spec, HINTS, stub does not already pass
./check --solutions lean ID     # the solution passes
python3 tools/guide_sync.py ID  # shape, guide compiles cleanly, states reached, no banned names, no spoilers
```
